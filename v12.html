Antes que nada

El sitio 404 en cualquier ruta que no sea "/"

No es contenido sin construir — es una configuración del hosting, y bloquea el acceso directo hasta a las secciones que ya funcionan.

ELI5

Si mandas por WhatsApp el link de una sección puntual (no el de la portada), a quien lo abre le sale una página en blanco con error. No es que falte programar nada ahí — es un interruptor mal puesto en el hosting. Se arregla en minutos, no en días.

Falta el fallback de SPA

Confirmado de dos formas independientes: pedir https://ceicusach.cl/wikiprofes directo devuelve HTTP 404 del servidor (no un 404 dibujado por React), y al abrirlo en un navegador la página queda en blanco con errores 404 en consola para los recursos de esa ruta. El sitio es una SPA (React + Vite, ruteo en el cliente) — funciona si navegas haciendo clic en los links desde "/", pero cualquier acceso directo a una ruta interna (recargar la página, un link compartido, un resultado de Google, un marcador) muere en un 404 real, incluso para secciones que ya tienen contenido real como Nosotros o Programa.

Impacto: nadie puede compartir un link directo, nadie puede recargar sin perder la página, y Google no puede indexar nada más que el Inicio.

El arreglo: decirle al hosting que sirva index.html para cualquier ruta que no sea un archivo estático, y dejar que el router resuelva la página en el navegador.

Confirmado con tus propios headers: al recargar /wikiprofes la respuesta trae server: cloudflare y cf-ray, con content-length: 0 — un 404 con cuerpo vacío, típico de Cloudflare Pages cuando no hay ruta que haga match y no existe un _redirects de respaldo. Empieza por la pestaña Cloudflare Pages de abajo; si el dominio en realidad está proxied por Cloudflare hacia otro origen, el panel de hosting real lo confirma, pero el cuerpo vacío apunta directo a Pages.

Crea public/_redirects (se copia tal cual al build):

# public/_redirects
/*  /index.html  200

Crea vercel.json en la raíz del proyecto:

// vercel.json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

Igual que Cloudflare Pages — public/_redirects:

# public/_redirects
/*  /index.html  200

Dentro del bloque server {} que sirve el sitio:

location / {
  try_files $uri $uri/ /index.html;
}

Cómo verificar: recarga ceicusach.cl/wikiprofes directo en una pestaña nueva (no navegando desde el Inicio). Si carga el contenido en vez de quedar en blanco, está arreglado.

Antes de construir

Cómo mantener esto sin que se vuelva un problema

La base (React + Vite + Tailwind, ruteo en cliente) está bien elegida — sigan con eso. Tres decisiones evitan trabajo doble más adelante, y una cuarta nota resume qué tan seguro se puede estar del stack sin ver el repo.

ELI5

Tres decisiones chicas ahora ahorran mucho trabajo repetido después: usar un solo componente para las páginas parecidas, compartir la lista de ramos entre BuscaCursos y la Malla, y aprovechar que ya se está usando el truco de "mandar a una carpeta de Drive" para lo que no vale la pena construir a mano.

01 — Contenido
Noticias, Actas, Transparencia y Documentación son, en el fondo, la misma estructura: una lista de entradas con fecha, título y a veces un link o PDF adjunto. Constrúyela una sola vez como un componente "lista de entradas" que lee de un manifiesto de datos, y esas secciones se vuelven configuración, no código nuevo cada vez. Importa doblemente porque quien actualice Noticias el próximo semestre probablemente no sea quien programó el sitio.
02 — Un solo catálogo de ramos
BuscaCursos ya trae el catálogo de ramos de ambas menciones (PROGRAMS.ingeco y PROGRAMS.economia). Malla Interactiva debería leer ese mismo dataset, no armar uno paralelo — así un cambio de malla se actualiza en un solo lugar en vez de en dos proyectos que se pueden desincronizar.
03 — El patrón "carpeta de Drive" ya funciona, úsenlo a propósito
Al revisar las páginas guardadas encontré que Actas, Apuntes y parte de Transparencia ya resuelven el contenido enlazando a una carpeta de Google Drive compartida en vez de construir un visor dentro del sitio. Es una decisión válida para una organización estudiantil — mucho más barata que programar un visor de PDFs, y quien sube el archivo no necesita saber nada de código. Vale la pena mantenerla a propósito (no como algo "provisorio" que hay que reemplazar) para Noticias y Documentación también, reservando componentes nuevos solo para lo que de verdad necesita interactividad, como Malla o el foro de preguntas de Transparencia.
04 — Lo que el HTML guardado confirma del stack (y lo que no)
Sin repo, esto es lo más cerca que se puede estar de "seguro" mirando solo el navegador. Cada página guardada carga index-C37R1YOy.js como type="module" más un CSS con hash (index--NXPsfBS.css) — nombres de archivo con hash de contenido es la firma de un build de Vite. Cada página también precarga ( modulepreload) los chunks de todas las rutas del sitio a la vez (malla-*.js, noticias-*.js, wikiprofes._slug-*.js, etc.) — y ese último nombre, wikiprofes._slug, es la convención de nombres de rutas dinámicas de React Router (v6.4+/v7) en modo "file-based routing" (un archivo tipo wikiprofes.$slug.tsx se compila con ese nombre). Eso confirma con bastante seguridad: Vite + React + React Router con rutas por archivo, Tailwind (clases utilitarias como block-border son propias del proyecto, no de Tailwind puro — hay una capa de componentes/clases custom encima) e íconos lucide-react.

Enfoque técnico

Es scripteable, no manual, pero es trabajo real a presupuestar (pendiente). 4) Una vez estén los prerrequisitos, resaltarlos al hacer clic en un ramo — sin librería de grafos para la v1 (pendiente).
